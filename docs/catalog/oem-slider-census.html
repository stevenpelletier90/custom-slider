What the OEM demo sliders actually are

The demo estate is 154 live hostnames — 129 distinct sites once 25 redirect aliases are folded in. The 76 known on 18 Aug were fully fingerprinted that day; an exhaustive hostname probe then surfaced 53 more real sites, fingerprinted 19 Aug. The variety is mostly skin: the fading hero we could not build until this week is the most common pattern of all. A second sweep also followed one site per brand onto its inner pages — the numbers for that are further down.

The finding that changed our plan

68 of 76 sites run a fading hero banner — and until this week our slider could not do it at all.

That makes the fade hero more widespread than the model bar. Earlier research missed it because it is a Bootstrap carousel-fade, not slick: the word fade appears in 0 of 55 slick configs. Every one of them rotates on a 5-second timer, which we confirmed by watching a live page advance rather than trusting the markup.

Fade mode shipped on 18 Aug. The gap is closed.

Five types, and where we stand

Counted by distinct sites across the 76 fully fingerprinted on 18 Aug — the baseline every section down to the platform-hero comparison uses. The "same across OEMs" question resolves here: one pattern covers 55 of the 76. One qualification from the 19 Aug estate sweep below: on the newer sites, four homepages replace the carousel with a background-video hero and one lays its model strip out as a static CSS grid — so "five types cover everything" is exactly true of the 18 Aug baseline, and nearly true of the full 129.

Centre-mode and the two-row grid were first filed as out of scope, assuming they needed engine work. Re-tested on 18 Aug, neither does — both are CSS on top of what already ships, so every slider pattern in the estate is now buildable. The one entry that stays out is Mazda’s filter UI, which is not a carousel.

The model bar is one design, not fifty-five

Every model bar in the estate shares an anatomy. These are the option settings, counted across all 55:

arrows: true 55/55
autoplay: false 55/55
swipeToSlide: true 55/55
slidesToScroll: 1 53/55
centerPadding: 60px 53/55
dots: absent 52/55
fade: absent 55/55

Three of those settle open questions for us: slidesToScroll: 1 is exactly what data-step="slide" reproduces, centerPadding: 60px is our --dlc-peek, and not one model bar in the estate autoplays — which is why no card strip in our library ever will.

One asterisk from the 19 Aug estate sweep: groupdemo1 runs two autoplaying strips — a 7-up OEM-logo strip and a 4-up dealership-location strip, the first autoplay found on any homepage card strip. Neither is a model bar (.makes and .locations, not .modelBarS), so the 55/55 above still holds for model bars across all 129 sites.

The homepage census left the rest of each site unexamined, so a second sweep followed one demo site per brand inside — SRPs, VDPs, model detail pages, specials, service and about/staff. 32 sites were attempted; 24 had their full page set reachable, and every count below comes from those 24. The platform’s newest slider already works the way ours does: every VDP runs a native scroll-snap photo gallery, and slick is not even loaded on the page.

DealerOn’s own VDP gallery (vehicle-image-carousel) is a CSS scroll-snap track with arrows, a counter and thumbnail strips — architecturally the same bet dl-carousel makes. The other universal pattern is its opposite: every SRP ships slick.min.js plus the full slick CSS with zero static init, for a per-vehicle-card carousel that is injected entirely at runtime.

The static-HTML caveat. SRP vehicle cards are client-rendered from an API, so the biggest inner-page slider surface — the per-card carousel on every SRP — cannot be seen in a static fetch. What can: the slick assets ship on every SRP with no init anywhere in the HTML, and the card data carries a photo-list model for it. Confirming which library actually renders it needs a browser pass, which has not run yet.

The dead-weight argument writes itself. Ford’s Maverick page still loads slick and still calls it — on markup that is commented out. And every SRP estate-wide carries slick’s JS and CSS for one runtime card carousel; dl-carousel’s entire budget is under 6 KB gzip, less than that freight before counting jQuery.

How this was counted

Method, and the two things it got wrong first
  • The roster came from probing the <oem>demo<N>.dealeron.com convention, since the Salesforce Knowledge article needs a login. 76 hosts across 32 brands responded. chevydemo* is not the convention — chevroletdemo* is.
  • All 76 homepages were fetched and parsed with balanced-delimiter extraction of every slick init and its config. <style> blocks are stripped first — the platform bundles Bootstrap's CSS everywhere, which otherwise reports a carousel on all 76 sites whether or not one exists.
  • Corrected once: the first pass counted slick init calls, but one $('.modelBarS').slick() initialises every matching element. Counting elements instead is what revealed that 30 sites run multiple grouped model bars.
  • Corrected again: the pause control appears in zero of the 76 HTML sources, which looked like it was simply missing. It is injected at runtime — visible only on the live page. Anything behaviour-dependent here was checked in a real browser for that reason.
  • The inner-page sweep (19 Aug) is static HTML only. One demo site per brand, ~190 pages by curl: 32 sites attempted, 24 with the full page set reachable — the inner-page counts use only those 24, and no live-browser pass has run on them yet. The runtime-injected SRP card carousel is the known blind spot.
  • The estate sweep (19 Aug) is also static HTML only — the 53 new sites have had no live-browser pass, and their "looks" are read from markup and CSS, not screenshots. The hostname probe ran every brand stem times indexes 1–14 plus the combined-brand and genre stems; two alias targets (dealer17728, dealer26244) land outside the demo naming set and stay unanalyzed. The Salesforce Knowledge roster is still behind Lightning auth, so the probe has not been reconciled against it — a demo on an unconventional hostname would be missed exactly the way buickgmc/cdjr/group were the first time.
